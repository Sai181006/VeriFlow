# VeriFlow presentation speaking script

**Presenter:** Sai Mohita.C, 24BCE2057

**Deck:** `VeriFlow-Research-Presentation-2026-10-30.pptx`

**Pace:** About 8–10 minutes. The sentences below can be read aloud; pause to point to the screenshots and results.

## Slide 1 — Title

“Good morning. I’m Sai Mohita.C, registration number 24BCE2057. My project, VeriFlow, is a small compiler and migration system for typed CSV pipelines. The code is available at the GitHub link on this slide. I’ll show the research question, the evidence, and then the three compiler phases running.”

## Slide 2 — Core idea

“A schema can lose information without changing what a particular pipeline does. Here, converting 5.7 to the integer 5 changes the result of `score > 5`, but it does not change `score >= 5`. VeriFlow examines the pipeline’s actual operations and output, rather than judging the migration only by whether a record is lossless.”

## Slide 3 — Related research and gap

“Recent work studies ETL repair, robust cleaning pipelines, provenance-assisted inversion, and query equivalence after migration. Those ideas are important prior art. My narrower question is whether a typed row pipeline can still produce the same observation after an explicitly lossy change, and whether that decision can be executed for each migrated row. I do not claim to have invented provenance or schema adaptation.”

## Slide 4 — System map

“VeriFlow starts with the old pipeline and an explicit schema mapping. Impact analysis follows the fields that operations and output can observe. The compiler creates bindings from new-schema cells into the existing VM. Migration then admits a row with a valid guard, retains a needed old cell, or rejects the row; disk replay checks that the old and evolved observations match.”

## Slide 5 — New council-selected feature

“The last internal review recommended one bounded improvement. If a row is filtered, rejected, or errors before `select`, a field used only by `select` cannot affect that row’s result. The executor now defers that field until emission. In the real ICU workload, this saves the old `vent_sari` value for 4,025 emitted rows and omits it for 3,290 filtered rows.”

## Slide 6 — Compiler architecture

“The compiler has three broad phases. The front end produces tokens and a syntax tree. The middle end checks types, lowers expressions to intermediate instructions, and optimizes them. The back end generates executable stack-machine bytecode and runs it. The migration extension reuses those phases by compiling new-schema field bindings around the existing VM program.”

## Slide 7 — Phase 1 output

“These are real terminal captures from the project. On the left, the lexer turns the `.vfl` source into positioned tokens such as `SCHEMA`, identifiers, and types. On the right, the parser has built an abstract syntax tree containing the schema and pipeline. This stage catches malformed source structure before execution.”

## Slide 8 — Phase 2 output

“Semantic analysis resolves field names and types; this is where an unknown field or invalid expression is rejected. The right screenshot shows the logical plan and postfix expression IR. The intermediate representation gives the optimizer an explicit instruction sequence to transform safely.”

## Slide 9 — Optimization

“For this demo expression, constant folding, arithmetic identity removal, and Boolean simplification reduce the expression from 21 instructions to 13. The right screenshot is the optimized intermediate output. That is a 38.1% instruction-count reduction in this sample; I am not claiming a measured general runtime speedup from it.”

## Slide 10 — Phase 3 output

“The back end emits VM instructions such as `LOAD_FIELD`, `PUSH_INT`, `ADD`, and filter jumps. The left capture is the generated bytecode; the right capture shows the program executing and writing two rows while filtering one. So the code-generation output here is executable VM bytecode, not generated Python source.”

## Slide 11 — Data and evaluation design

“The strongest external evidence is a documented Malaysian Ministry of Health ICU CSV change: 7,315 matched before-and-after rows, a removed field, and four renamed fields. I also use Abalone, Iris, and Red Wine Quality to inject controlled lossy conversions. The ten injected cases reuse 5,926 distinct rows, so their 17,928 case-rows are repeated workloads, not independent records.”

## Slide 12 — Real-history comparison

“For the pipeline that selects the dropped field, sparse replay accepts all 7,315 rows and retains 4,025 old cells. Full-row retention keeps 36,575 old cells. Guard-only rejects every row, so its smaller output is not evidence of preserved coverage. Both accepting strategies have zero observed typed mismatches, and sparse uses 89% fewer retained cells than full-row on this workload.”

## Slide 13 — Persisted execution

“This screenshot is an actual `migrate-run` followed by `replay-migration`. The bundle stores migrated rows, row IDs, a ledger, retained cells, and the compiled plan. Replay emits 4,025 rows and filters 3,290. The accepted migrated rows also match the official post-change CSV projection, so this is checked against a real paired history as well as the old pipeline’s typed observations.”

## Slide 14 — Synthetic pilot

“Strict-threshold guards admit about two thirds of Abalone and Iris rows, and about three quarters of Red Wine rows. Sparse recovery handles the remaining rows by retaining needed old values. Across the ten injected cases, sparse mode admits 10,379 case-rows and recovers 7,549, with no observed replay mismatch. The negative controls and CSV parity checks test failure paths too.”

## Slide 15 — Assessment and next step

“The implementation supports a focused research prototype and a live compiler demonstration. The claim is limited to well-typed old rows at migration time and deterministic row-wise operations. It does not certify arbitrary future new-schema rows. For a stronger full paper, the most useful next step is a second independent real lossy history and a directly comparable baseline, followed by external review of the proof.”

VeriFlow’s contribution is the scoped executable combination of typed pipeline observations, guards, compiled bindings, selective retention, and persisted replay. Thank you; I can now show any phase or migration command live.”
